## Modules
Decision: modules are single files or `mod.ace`-rooted directories; explicit imports; explicit exports.
1. A single-file module consists of one `.ace` file. A directory module consists of `mod.ace` and every implementation file recursively beneath its directory; `mod.ace` is its sole external import surface. Each file lists exactly what it imports; after compile-time-inactive declarations are removed, import statements precede every other declaration — reading order is stated up front for the in-order check. A subdirectory with its own `mod.ace` is itself a nested module, addressable via a `/`-separated path from any enclosing directory: bare `import net/tcp`, aliased `import bla: net/tcp`, or quoted relative `import "../A/B"` (the same `/` separator; a quoted path without a `.ace` suffix resolves as a nested-module path instead of a flat file). A subdirectory without `mod.ace` stays private, swallowed by its nearest enclosing module boundary exactly as an ordinary implementation file. Only the leaf segment's identifier becomes the bound qualifier — `import net/tcp` brings `tcp` into scope, not `net` — mirroring single-segment `import tcp` binding `tcp`. There is no transitivity in either direction (rule 9): importing `net/tcp` exposes nothing through `net`, and importing `net` does not expose `tcp` unless `net`'s own `mod.ace` explicitly re-exports it.
2. Members are private unless marked `pub` on the declaration line — `pub max(a: int): int`; the mark lives with the member and cannot drift; one grep finds every public member. Applies to types, functions, and globals alike. In a directory module, `pub` in an implementation file grants access only to other files beneath that directory module, its nested modules' files included. Only `pub` declarations owned by `mod.ace` are externally visible. A program's own path-imported files are its internal scope: a `pub` there reaches only the program's files that import it, so a program shares a private helper by making it `pub` in one file. A facade re-exports a type explicitly with an ordinary public transparent alias, such as `pub Fd: type = os.Fd`; imports themselves never re-export.
3. A struct field is private unless marked `pub` on its line (`pub len: usize = 0`), and its visibility is computed exactly as a declaration's under rule 2, relative to the file declaring the struct: an unmarked field is visible only in that file, and a `pub` field is visible wherever the struct is visible, never wider. A facade's public alias of the struct (rule 2) makes the struct, and so its `pub` fields, visible to importers. Outside its visibility a field cannot be read, written, named in a struct literal, or set positionally. An empty literal `T {}` and `blank(T)` name no field and remain available everywhere the type is: they yield only the declared defaults and canonical zero. Embedding never widens a field: `x.base.f` is checked against `f`'s own declaration. [`pub` spelling provisional]
4. Compilation reads imports in dependency order, reading only what is imported — nothing scanned, nothing implicit. **Import cycles are a compile error** (a cycle has no first file; structure, not policy).
5. Incremental rebuild granularity: the file.
6. Whole-module imports remain qualified: `import math`, then `math.sqrt(x)`. Aliasing resolves qualifier collisions (`import m: math`), `import util: "./util.ace"` loads a relative local module, and compiler-reserved standard-library implementation uses the visibly distinct `import big: @bigint` form.
7. Selective imports explicitly place public member names into their ordinary namespaces: `import min, max from math`, or `import Point, origin from "./util.ace"`. A bare member list stays on one physical line; the multiline form is `import (` followed by a comma-terminated member list and `) from module`. `from` is recognized contextually only after the member list; it remains an ordinary identifier everywhere else (`from: usize = 0`). A selected function name imports its complete public overload set. Visibility is per overload: an importer, qualified or selective, sees only a set's `pub` overloads, as if the rest were absent; a name with no `pub` overload is not public. When a module exports both a public type and public value under one spelling, selection imports each into its separate namespace; visibility is independent across the two namespaces.
8. A selected name conflicts with another import or declaration in the same namespace and scope; imports from different modules never merge overload sets. Nested lexical scopes may shadow selected value names under the ordinary nearest-binding rule. On a collision, import the module qualified instead. Only `pub` names may be selected; the source may be a bare standard module or relative `.ace` path.
9. An import grants the importing file the right to use imported names and never re-exports them. A module's public surface is exactly its own `pub` declarations; imported names are invisible to consumers, who import the modules they use through their own explicit imports.
10. A resolved module path is canonicalized before cache lookup and deduplication. Lexically different paths containing `.` or `..` that resolve to the same file produce one module instance and one set of declarations. This changes neither import scope nor the supported standard/relative import forms and adds no search path.
11. OS- or kernel-specific standard-library code always sits behind a stable public facade at `std/<module>/mod.ace`; target implementations live under `std/<module>/os/<target>.ace` and are selected through `@when(target == "...")` imports in that facade. Public callers cannot import an OS file directly. The target file exposes exactly the operations and types required by its facade; it does not add same-signature target-named forwarding functions. Those declarations are `pub` only within the directory module and carry no compatibility promise outside it. The `os` name is reserved by convention for this implementation layer; `backend` refers to compiler/code-generation backends and is not used for OS bindings.
12. `@when(condition)` is the sole conditional-compilation form and attaches to exactly one top-level declaration, including an import, function, type, global, signing, or extern block. The attribute occupies its own line and a preceding top-level construct is separated from it by one blank line. Its deliberately closed boolean expression language contains `true`, `false`, `target == "name"`, `target != "name"`, contextual `and`/`or`/`not`, and parentheses. `target` is the compiler-selected build target string; it defaults from the host and may be overridden with `--target=NAME`. A target name is `<os>-<arch>`, two hyphen-free parts: `darwin` or `linux`, then `arm64` or `x64` (the Node, Bun, esbuild, and .NET spellings), so it splits at its one hyphen and both architectures share one convention. Unsupported targets are rejected rather than implying an unavailable backend or standard-library layer. The compiler lexes and parses an inactive declaration, so its syntax must be valid, then removes it before import loading, binding/duplicate checks, semantic analysis, and emission. Thus mutually exclusive imports may bind the same alias and mutually exclusive declarations may share a signature; if more than one matching declaration survives, ordinary duplicate rules apply. There is no block, statement-level form, user-defined build flag, arbitrary constant evaluation, or runtime condition. A file need not provide an exhaustive arm, but any surviving reference to an absent declaration fails normally.
## Package System (future work)
Decision: packaging is an optional, explicit layer above file modules; one `ace` executable owns both the direct compiler and the separately grouped package commands. Every dependency is found in a reserved `pkg/` directory; remote installation into it (#9) and manifest syntax remain open for later carving.
1. `ace.pkg` at a package root defines exactly one package and one primary output. Every package explicitly declares `type` as `exe` or `lib` and explicitly names one root `.ace` file. An exe package produces an executable and its root must provide `main(): int`; a library exposes its root module as its sole external import surface. Consumers cannot deep-import its internal files. A library is distributed as source; initially, `ace pkg build` checks its complete graph and produces no reusable binary archive.
2. A package has a required name, exact package version, and Ace language version. The name is case-sensitive, must be lowercase, and follows the Ace identifier shape; its source location is separate from its identity. Package versions are exactly three nonnegative components (`major.minor.patch`) with no initial prerelease/build suffixes. The Ace field names one exact `major.minor` language version, not a compiler release. Every package in one build graph must use the same Ace language version.
3. Required build fields are package name, package version, Ace language version, type, and root. Description, authors, license, repository, and homepage are optional informational metadata and never affect identity, resolution, or compilation. Exact `ace.pkg` structure, delimiters, and field syntax remain [open].
4. A dependency declares only its canonical name and one exact version (`json: 0.1.0`); ranges and implicit latest selection do not exist. The sole dependency source is a `pkg/` directory (#5): a dependency is never located by a path, URL, or other per-dependency source.
5. Every dependency name in a graph, direct or transitive, resolves from the directory of the package being built: the first existing `<dir>/pkg/<name>` found by checking that directory and then each ancestor directory in turn. The nearest match is authoritative and its root `ace.pkg` must declare the requested name and version; a mismatch is an error rather than a reason to keep searching. A dependency's own `pkg/` is never consulted, so the layout is flat and each name has one location per graph.
6. `pkg/` is reserved at every package root. It is not part of the package's own canonical directory: a package root file cannot live under it, and a relative import cannot reach into it.
7. A package may import only dependencies declared directly in its own manifest. A dependency root uses the existing module syntax (`import json`, selective imports, and source-level aliases); package names may not collide with standard-library module names. Manifest dependency names are canonical and cannot rename a package. Every root and relative import must remain within its canonical package directory.
8. The complete dependency graph is acyclic and contains at most one version of each package name. Conflicting versions, identities, or cycles are errors showing the relevant dependency paths. There is initially one ordinary dependency set, selectable per target only through a qualified `[dependency: …]` section (#16): no dev, test, optional, peer, or feature-selected dependency classes.
9. Remote packages are [open]: one central registry or resolver maps a package name to its published source and installs it into `pkg/`, so every dependency keeps one uniform source rather than a mix of URLs, repositories, and local paths. Fetching, updating, remote version listing, any lockfile, and their tooling are carved with it.
10. `pkg/` is where package installation writes and is normally excluded from version control; the compiler does not enforce this, and a project may commit its `pkg/` to vendor its dependencies. Only one version of a named package can be installed in one `pkg/`.
11. Plain `ace` remains the direct compiler interface and standalone source compilation does not require a manifest. Every manifest-aware operation is grouped under `ace pkg`: the initial commands are `init`, `build`, `run`, `check`, `add`, `remove`, and `list`. `run` is exe-only and passes the arguments after `--` to the program. `init` creates a minimal exe or library without overwriting existing files. From a subdirectory, package commands find the nearest enclosing `ace.pkg`; a nested manifest starts an independent package. `--dir=DIR` starts that search in `DIR` instead of the working directory, for every command but `init`.
12. `ace pkg add name version` and `ace pkg remove name` edit the manifest and validate the complete graph atomically; failure leaves the manifest unchanged. Neither writes or deletes anything under `pkg/`. Build, run, and check never modify `pkg/` and diagnose a missing or mismatched dependency by name, version, and the directory that was checked.
13. `ace pkg list` reports the resolved graph, including each package's direct/transitive relation and resolved directory. Exact display and flags remain [open].
14. Arbitrary shell scripts, lifecycle hooks, publishing, and releasing are excluded initially. Any package (`exe` or `lib`), not only the root, may declare native link inputs, each one exact file named in its manifest or a platform framework; the build never searches for a library, infers a file name or extension, or falls back to the linker's search. Declared in `[link]` sections (`GRAMMAR.md` §7, target selection #16), each line one input: `path: FILE`, linked as written, or `framework: NAME`, a bare platform framework name the toolchain resolves in its active SDK (fixed by the platform, unlike a third-party library), passed as `-framework NAME` once per name. A section may repeat either key. A relative path resolves against the declaring package's own directory with no `..` traversal, matching the import-containment rule (#7), and must exist when the manifest loads; an absolute path names a host file, checked only when it is the one linked. An exe's final link step collects the transitive union of every declared file in its dependency graph, ordered dependency-before-dependent with each package's declaration order preserved, each file name (its basename, the input's identity) linked once at its first position. The root package's path for a file name overrides every dependency's; otherwise two dependencies declaring one file name at different paths are a resolution-time error naming both, mirroring the one-version-per-package-name rule (#8), which the root settles with its own path. The linked file must exist. A `lib` package's declared inputs stay dormant metadata until some `exe` in the graph reaches the link step (#1). Custom code generation, deployment, assets, and unrelated tasks stay with an external build tool. A future `tls` client transport (carved from philosophy/semantics; see issue #65) gates on this: whether it belongs in `std` or launches as a package depends on native link-input declarations landing here.
15. Conventional output paths keep the manifest small: an exe defaults to `build/<package-name>`, library build state stays under `build/`, and an explicit command-line output path may override an exe build. Exact package command flags remain [open].
16. A manifest section header names its kind in the singular (`[dependency]`, `[link]`) and may carry one target qualifier, `[link: darwin-arm64]`: a full target name (Modules #12, `<os>-<arch>`) or an OS alone (`darwin`, `linux`), matching every target of that OS. An unqualified section applies to every target. When building target T, the active sections are the unqualified one and those whose qualifier is T or T's OS, taken in file order; the others are parsed, then dropped, and their paths are never checked. An unknown qualifier, and a repeated header (the same kind with the same qualifier, or none), are errors. Only active sections take part in resolution, link collection, overrides, and conflicts. Negation and alternatives are not expressible; a condition that needs them repeats the section per target.

## C Interop
Decision: one explicit `extern "c"` boundary in both directions; Ace internals stay free.
1. Ace-internal symbols may be mangled (multi-return, mut params, modules) — mangling is private to the compiler.
2. `extern "c" { … }` blocks state the ABI once for their declarations. A declaration without a definition imports a C symbol; a function with a body is defined in Ace and visible to C under its unmangled name. `extern "c" name(…) { … }` is the single-definition form, which may be `pub` or `inline`. Variadics (`…`) are legal only in imported declarations (Functions & ABI #7). A definition may carry a link name too (`extern "c" triple(v: i32): i32 as "ace_triple" { … }`), exporting it to C under that symbol while Ace code keeps the Ace name; two definitions exporting one symbol are a compile error. An imported declaration may carry a link name — `c_open(path: *u8, flags: i32, mode: u32): i32 as "open"` (`as` is contextual) — binding an Ace-side name distinct from the linker symbol, which lets a module wrap a C function under the name it wants to own (first customer: `sys`). The linker spelling is always the declared (or link-named) symbol with the platform's underscore convention applied by the compiler. Link names must be nonempty, contain no NUL byte, and in the v1 emitter are limited to 510 decoded bytes; other bytes are accepted because platform symbols need not be C or Ace identifiers.    Implementation note (Apple arm64): C variadic functions receive their unnamed arguments in 8-byte caller-stack slots, not in the remaining argument registers — libSystem's `open` itself reads mode from the first stack-argument slot. The emitter implements that convention, including the ordinary f32-to-f64 and `bool`-to-`int` default promotions. The initially verified unnamed-argument set is C-compatible integer, `bool`, floating, distinct-scalar, and pointer values; aggregate and Ace-specific shapes are rejected until their variadic ABI is separately verified. A fixed-surface wrapper may still bind a fixed-arity export such as `__open` rather than expose variadics it does not need.
3. C-facing signatures are checked by a positive, position-aware C-ABI compatibility predicate (chunk 1B decision). Allowed: the fixed-width integers `i8 i16 i32 i64` and `u8 u16 u32 u64`, the platform words `int`/`uint`, `usize`, `f32`, `f64`, `bool` (C `_Bool`, Type System #12); explicitly backed enums, represented exactly as their fixed-width backing integer (a closed enum C returns, writes, or passes to a callback must hold a member; a C enumeration that can grow is declared open, Type System #15); plain and writable pointers (`*T`, `mut *T`) whose pointee shapes are recursively compatible; distinct types whose bases are allowed in the same position; structs whose fields are recursively compatible; arrays whose elements are recursively compatible only when nested inside a compatible aggregate or behind a pointer; and explicitly `extern "c"` function values in every position. A no-value (void) shape is allowed only as a function return. Direct array parameters and returns are rejected. Rejected: default enums without an external width promise, `string`, slices, contracts, tagged unions, `Error`, error domains, `typeid`, every tuple shape, ordinary Ace function values, type parameters, generic declarations, and generic instantiations. `mut` parameters stay internal-only — writable storage crosses the boundary as an explicit `mut *T` (the former `mut p` → `T*` export mapping under Functions & ABI #6 is struck). The recursive check carries a cycle guard so C-compatible self-referential structs through pointers terminate correctly. Every rejected category is additive later, each only after an exact C representation is separately approved.
4. Ace programs never depend on another programming language or its utility
   runtime — interop is a declared boundary, not a foundation. Ace language and
   standard-library behavior is implemented in Ace or emitted directly. A
   target facility is reached through the OS's stable public interface first;
   when a direct syscall is unavailable or not a stable application contract,
   target code uses the system library or framework supplied by that OS. Thus
   Darwin uses libSystem for OS services, process services, the selected
   process-wide allocator, and comparable platform facilities rather than
   private kernel entry points. This permission is purpose-based: a symbol's
   presence in libc, libSystem, or another system library does not justify using
   another language's sorting, searching, string, memory, numeric-conversion,
   formatting, or other convenience implementation. User programs remain free
   to opt into explicit interoperability. The bootstrap compiler's C11 source
   and its ordinary C implementation facilities are a build-time choice, not
   part of Ace program semantics or the generated runtime model.
5. A callable C function-pointer type is spelled `extern "c" (P1, P2): R`;
   zero parameters use `extern "c" (): R`, and no value is `: void`
   (`extern "c" (): void`), as for every function type (Syntax & Parsing #5).
   Its parameters and return independently satisfy the positive C-ABI
   whitelist, and variadic, generic, and non-`c` function
   types are rejected. The value is one pointer-sized word with canonical zero
   `null`; equality with `null` is ordinary function-value equality. A debug
   build diagnoses calling null and a release build assumes the callee is
   nonnull. An `extern "c"` definition or imported declaration with
   the exact signature is referenced by its bare name under an explicitly typed
   destination; an ordinary Ace function never converts to this type. Calls use
   the platform C convention in both directions. C function values are
   plain bits (Memory, untyped storage) and are admitted wherever a data
   pointer is: parameters, returns, struct fields, and pointees. There is no address sigil,
   closure, captured context, lifetime management, generic callback, calling-
   convention inference, or arbitrary foreign ABI.
6. An `extern "c"` block may declare a C global variable as `name: type`,
   with an optional link name as for functions (`c_out: *File as "__stdoutp"`).
   It binds C's storage; it defines, allocates, and initializes nothing. It is
   read-only unless marked `mut` (`mut opterr: i32`), as with `*T` and
   `mut *T`, since C `const` data may sit in read-only memory. The type passes
   the C-ABI whitelist (#3) at struct-field position, so a fixed array is
   allowed. A use reads or writes the C storage in place, and `&name` is `*T`,
   or `mut *T` when `mut`. A read is never assumed unchanged across a call or
   asm. Thread-local C variables are not supported; C libraries reach them
   through accessor functions, which an extern block already binds.
   A global with an initializer is defined in Ace and visible to C under its
   unmangled name, or under its link name (`name: T as "sym" = value`): `mut ace_counter: i32 = 0` in the block, or the single form
   `extern "c" [mut] name: T = value`, which may be `pub`. It is an ordinary
   compile-time-constant global with the same C-ABI type rule, read-only unless
   `mut`, and a read-only one is placed in read-only data.
7. A C `longjmp` that unwinds through an Ace frame is undefined behavior, since it skips that frame's deferred calls. A `longjmp` whose `setjmp` and every skipped frame are C is ordinary C and unaffected. Ace has no way to establish a jump target, and the compiler does not model a function that returns twice, so `setjmp` is not callable from Ace. A library that makes its caller the catch point is reached through a C shim that calls `setjmp`, returns normally, and never lets a `longjmp` cross an Ace frame; the compiler does not detect a crossing.
