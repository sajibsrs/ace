## Compiler
1. Make memory size available to programmer. (see: Errors)
2. Compilation is a fixed sequence of in-order passes, with no whole-program or cross-function analysis:
   1. Lex: one scan of a source file into tokens.
   2. Parse: one recursive-descent pass from tokens to an AST; inactive `@when` declarations are dropped here.
   3. Merge: each imported file is lexed and parsed the same way, renamed through one loop over its top-level declarations and one scoped reference walk, and merged into one unit in dependency order.
   4. Check: one loop enters every top-level name except functions; one in-order walk completes every type, then one in-order walk over the unit checks the rest. A declaration a lookup needs before its turn is resolved on demand (#5). At end of file: top-level checks (specialized generics, contract method sets), resolution of pending forward calls, a second check of only the bodies that made one, a cycle walk over `inline` functions only, and one definite-initialization walk.
   5. Lower: one walk of each checked function into SSA (Braun et al., trivial phis removed), expanding `inline` calls (binding a receiver or `mut` argument that is a local, or a field of one, to its SSA variables unless something needs the local's address), turning `defer` into control flow, making debug checks trapping instructions (checked integer arithmetic) or explicit branches, splitting every struct, tuple, string, and slice into its scalar leaves (SSA values, or loads and stores for one that lives in memory; the IR has no aggregate values, and each target maps leaves onto its ABI), and turning self tail recursion into a loop.
   6. Optimize (release only), in this order, each once: sparse conditional constant propagation, global value numbering, loop strength reduction, dead-code and control-flow cleanup (which also sends a jump into a branch whose condition is constant along that edge straight to the arm it selects).
   7. Select AArch64 instructions, including fused forms (integer `madd`, never float contraction).
   8. Leave SSA: phis become copies, with coalescing.
   9. Allocate registers: linear scan over one interval per value, aware of calls, rematerializing constants and stack-object addresses. Interval splitting is added only if measured spills in hot code call for it.
   10. Lay out blocks (both modes: a header that only tests, with one back edge that is a plain jump, is laid out after its latch, so the loop ends in the test's own branch instead of a jump to the test; then the arms of `@cold` calls, Functions & ABI #10, go last, so the common path falls through) and encode; then globals, vtables, fixups, DWARF, and the Mach-O write.

   Passes 5–6 are shared by every target; 7–10 are per target. Each works on one function at a time, with no whole-program or cross-function analysis; explicit `inline` is the only crossing. Only reachable functions run them: starting from `main` and the C exports, each link symbol a compiled function references and no function yet defines names the next function to compile; an object without `main` compiles every function. A reachable function the IR does not cover is a compile error. A function body is walked by check once (twice after a forward call), by definite initialization once, and by lowering once. `--ir` prints the IR, as `--ast` prints the AST.
3. Name mangling — internal symbols only; the C boundary is explicit and unmangled (see: C Interop).
4. Code generation: a per-function SSA IR (#2 passes 5–10), from which Ace writes machine code and objects itself, with no external assembler or backend. Files: `src/ir.c` (IR, verifier, printer), `src/lower.c`, `src/optimizer.c` (pass 6), `src/regalloc.c` (the target-neutral half of allocation: block order, liveness, location sharing, the linear scan), `src/arm64.c` (selection, the target's registers, encoding), `src/x64.c` (the same for x64, and its runtime routines), `src/emit.c` (object driver, data, runtime routines), `src/macho.c` (Mach-O writer), `src/elf.c` (ELF writer). Targets: `darwin-arm64` (AArch64 / Apple arm64, the reference machine is Apple Silicon) and `linux-x64` (x64 / System V AMD64, ELF, glibc, an x86-64-v3 CPU: FMA3 serves `math.fma`), the second backend, which does not yet cover every function: one it cannot compile is a compile error naming what it lacks.
5. Top-level types, aliases, globals, constants, C globals, and imports are order-independent within a file: each is visible throughout the file wherever it is declared, and a lookup that reaches one not yet resolved resolves it first. Names declared in a function body stay declaration-before-use (Names & Scoping #10). A declaration whose resolution reaches itself is a compile error naming the cycle: a constant's initializer, an alias expansion, or a layout query (`sizeof`, `alignof`, `offsetof`, `blank`, an array length, `@align`) inside the type's own declaration; an inline layout cycle is Type System #7. Functions keep declaration-before-use, except that forward and mutual calls, including method calls on a struct, are handled by fixups; only the callee is exempt, so a forward call's arguments see what the call's position sees: emit a call to a placeholder, record the patch site, and patch the real address at definition. A function body that made a call resolved at end of file is checked once more after resolution, seeing only the declarations its first check saw apart from those calls, so their results are type-checked where used.
6. Performance plan (v1):
   - Passes rely only on facts a debug build checks, so a run that passes in debug computes the same result in release. They never reassociate or contract float operations, and debug checks keep their order. Three facts are stated but not yet checked, and each needs a debug check before a pass may use it: `noalias` on pointer parameters (Safety #7 checks slices only), non-overlap of read-only parameters (Functions & ABI #5), and memory written by inline assembly (Inline Assembly #5).
   - Build modes: release (the default) runs pass 6 and has no checks; debug runs no pass 6 and keeps runtime checks. Locals are SSA values in both. Optimization and checks are two independent internal settings, so an optimized-and-checked mode can follow a concrete need (for example, fuzzing parsers of untrusted input). Executable tests run in both modes, and a differential check compiles random programs in both and requires identical output.
   - Self tail recursion — release builds lower `return f(args)` in the body of `f` itself to a branch back to its entry, reusing its frame, when sharing that frame across levels is unobservable: no `defer` is pending and no local or by-value parameter of `f` lives in the frame; `main`, exported, and inline-expanding functions keep their calls. Calls to other functions are never lowered, and debug builds keep every call. It is an optimization, not a guarantee: recursion that must not overflow is written as a loop.
   - Inline expansion — every call to an `inline` function (Functions & ABI #8); release builds also expand a direct call to a small leaf function: a body of at most 24 syntax nodes that calls nothing but conversions and compiler-backed operations, within `inline`'s other limits, and not generic, `@cold`, `main`, recursive, or inside a self-tail-recursive function. Debug builds keep those calls. The function stays callable as before.
   - `asm` is one IR instruction: its "in" values as arguments, its "out" registers as projections, and its reserved registers (every binding and clobber) kept free of values live across it. It is never reordered or removed.
   - Auto-vectorization — release builds run a loop whose iterations are provably independent on the target's vector unit (NEON on AArch64), several lanes per instruction, with a scalar loop for the remainder. Only lane-wise operations are vectorized, each lane computing exactly what the scalar loop would, so results match debug builds bit for bit; a float reduction, which would need reassociation, stays scalar. Independence is proven per function from the loop itself and signature facts (`noalias`, Mutability #8, once debug-checked). The loop analysis and rewrite is a target-neutral optimizer pass over internal vector IR types that no source code names; each target only emits the vector operations. It adds no syntax and no user-visible type. Debug builds never vectorize. Explicit `std/simd` remains the route for code the vectorizer cannot prove safe or does not cover.
   - Excluded: automatic inlining beyond small leaf functions, and loop unrolling or instruction scheduling unless later measured.
7. The source entry point is `main(): int`; on Apple arm64 the platform consumes
   its low 32 bits as the process exit status.
8. The compiler emits Mach-O objects and uses the system toolchain for executable
   linking. Minimal DWARF provides source line tables and only the structural
   records required for discovery; variable/type records and unwind data are not
   emitted.

## Functions & ABI
1. Multi-return — decided (see: Errors). Returns are positional: types only, `(int, Error)`; names appear at destructuring, never in signatures. A call whose result tuple matches the signature exactly — same count, order, and identical types — may be returned directly: `return read()`. Anything else destructures and returns the values explicitly.
2. Multi-returns are laid out as anonymous structs: small ones ride platform registers, larger ones use the hidden return pointer — plain platform struct-return rules.
3. `mut` parameters pass the caller's actual address (writes visible to the caller); read-only parameters pass addresses too, but small ones may travel by value — identical observable behavior, legal codegen freedom (same class as copy elision).
4. Internal calling convention: the platform convention (SysV, AArch64, …) — debuggers, profilers, tracers, and the C boundary work unchanged.
5. Parameter aliasing: parameters may alias unless proven otherwise; debug builds may test overlap; read-only marks are the optimizer's facts.
6. C-definition mapping (`extern "c"` with a body): a single C-compatible return; parameters and returns must satisfy the C-ABI whitelist (see: C Interop #3). `mut` parameters and multi-return stay internal-only — writable storage crosses as an explicit `mut *T`. The former `mut p` → `T*` export mapping was struck by the chunk 1B decision.
7. No user variadics in v1 — pass slices explicitly; C variadic functions (printf) import via extern blocks only. Slice-sugar variadics are additive later if ever wanted.
8. `inline` is a declaration modifier, after visibility and before a receiver `mut`, on a function, method, associated function, generic template, or specialization with a body: `inline mix(value: u64): u64 { … }`, `pub inline mut Buffer.put(byte: u8) { … }`. It is a guarantee, not a hint: every statically resolved direct call expands in place, whatever the declaration order or module. Arguments are evaluated left to right and bound to the parameters — a read-only scalar as a snapshot; a `mut` parameter, a receiver, or a read-only aggregate as the argument's storage, as #3 permits — and each `return` joins after the expansion with the result. Inlined code carries the call site's DWARF line. The ordinary callable symbol is still emitted, so function values and deferred calls call it. An inline function's result may be any type, a type parameter included (each expansion stamps the body under its call's type arguments): an aggregate's leaves join as SSA values, and one of over 16 leaves goes to memory as a call's would. It takes no `noalias` parameter, and contains no `defer` or inline assembly; `intrinsic`, a bodiless `specialized` template, and `main` cannot be `inline`; each specialization marks itself; a cycle of calls among inline functions is a compile error.
9. A function, method, associated function, generic template, specialization, `extern "c"` declaration or definition, contract method, or function type takes at most 64 parameters; a method's receiver counts (a contract method's implicit one included), since it is an ordinary argument of the call. A call cannot exceed its callee's type, so the limit is checked only there; the variadic arguments of a C variadic call are not counted. An `extern` declaration of a C function with more parameters cannot be written.
10. `@cold`, an attribute line before the declaration, marks a function, method, associated function, generic template, or specialization with a body as rarely called; each specialization marks itself. It changes no result, only code layout: a block making a direct call to it, whose one predecessor is a two-way branch, is laid out after the caller's other blocks with each block reached only from such blocks (Compiler #2, pass 10). A call through a function value or contract is unmarked. A cold function is never expanded, so `inline` and `@cold` together are a compile error, and release builds never expand it as a small leaf; `main`, `extern "c"` definitions, and bodiless declarations cannot be `@cold`.

## Inline Assembly
1. `asm "instruction text" { bindings }` — a statement, never an expression; values flow only through the bindings.
2. Bindings name real registers of the target directly: `in: x0 = fd` wires an Ace value in, `out: x0 = ret` wires a register out to an Ace local, `clobbers: x16, x17` declares what breaks. AArch64 names `x0`-`x30`; x64 names the 64-bit general registers `rax`, `rbx`, `rcx`, `rdx`, `rsi`, `rdi`, `r8`-`r15`, never `rsp` or `rbp`, which hold the frame. A register of another target is an error. An `in` value is an integer literal or names a scalar local or parameter, and an `out` target names a scalar local or parameter; an aggregate or a global is rejected. Nothing implicit — the compiler emits plain moves around the block. No constraint language exists.
3. asm statements are never reordered or elided; clobbers are honored by surrounding codegen. A function whose asm reserves a callee-saved register (AArch64 x19-x28; x64 `rbx`, `r12`-`r15`) through any binding or clobber saves it at entry and restores it at exit, as the platform ABI requires.
4. The ISA is implied by the compilation target, and the compiler encodes the instruction itself. v1 instructions: AArch64 `nop`, `svc #imm`, `brk #imm`; x64 `nop`, `syscall`, `int3`, which take no operands. Nothing is implicit: a Linux `syscall` declares `clobbers: rcx, r11`.
5. Memory written through asm is the programmer's trust — debug builds do not trace it.

```c
ret: i64
asm "svc #0" {
    in:  x0 = fd, x16 = 3     // Apple syscall convention
    out: x0 = ret
    clobbers: x16, x17
}

asm "syscall" {
    in:  rax = 60, rdi = code  // Linux x64 exit
    out: rax = ret
    clobbers: rcx, r11
}
```
